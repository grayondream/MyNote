# 缓存失效优化

**摘要**:`glInvalidateFramebuffer` 常被当作一个图形 API 的便利功能，但它背后有一个更普遍的模式：当应用确知某段数据不会再被读取时，显式告诉系统，让系统跳过本应发生的数据搬运。本文按 OpenGL、Vulkan、CUDA UVM、CPU 缓存四个层级梳理这一模式的具体形态，给出可运行的代码示例，并讨论各自的时序约束与适用边界。目标读者是已经能写图形或 CUDA 程序、但想理解“为什么加了这一行带宽就降了”的开发者。

**关键词**——带宽优化；帧缓冲失效；分块渲染；统一虚拟内存；非临时存储


## 1. 引言

&emsp;&emsp;如果你写过移动端渲染或 CUDA 程序，可能遇到过这种情况：计算量不大，帧率或吞吐量却上不去；profiler 一看，瓶颈在内存带宽。其中一个常见来源是**系统在搬运语义上已经无用的数据**。

&emsp;&emsp;`glInvalidateFramebuffer` 是解决这类问题的一个入口。它的用法很简单，但很多人只把它当成“清屏的替代品”，没意识到它代表的是一类跨层级的优化思路。本文不提出新概念，而是把这条思路在四个层面上的具体形态摆在一起，配上代码，方便你在实际项目里判断什么时候该用、什么时候不该用。


## 2. 为什么“不搬运”能省带宽：分块渲染的视角

&emsp;&emsp;移动 GPU 普遍采用分块渲染（Tile-Based Rendering, TBR）。屏幕被切成小块（常见 16×16 或 32×32 像素），每个块在 GPU 内部的 Tile Buffer 上完成渲染，最后写回系统内存（DDR）。Tile Buffer 带宽高、延迟低，但容量很小，装不下整帧。

![](https://cdn.jsdelivr.net/gh/grayondream/MyImageBlob@main/imgs/deepseek_svg_20261104_1cc305.svg)

&emsp;&emsp;于是每个帧缓冲附件在渲染通道边界处都有两次潜在的主存往返：

1. **加载**：渲染开始前，把 DDR 中该附件的旧内容读进 Tile Buffer；
2. **存储**：渲染结束后，把 Tile Buffer 的结果写回 DDR。

&emsp;&emsp;如果某个附件的内容会被完全覆盖，或者渲染后不再被任何后续操作读取，那么这两次搬运中至少有一次是纯浪费。默认情况下，OpenGL ES 会**保留**帧缓冲附件，驱动没有先验信息去跳过写回。`glInvalidateFramebuffer` 做的就是补上这条信息。

&emsp;&emsp;一个典型场景是后处理：一个 pass 只有一个 draw call，渲染目标会被完全重写。如果在绑定帧缓冲后、绘制前不发出提示，GPU 会先把旧数据从 DDR 读进 Tile Buffer，产生额外读带宽；加上失效调用后，这次读取就被消除了。反过来，如果深度/模板附件在 pass 结束后不再使用，在 pass 结束前失效它，就能省掉写回。


## 3. 四个层面的具体形态

### 3.1 OpenGL：运行时失效提示

&emsp;&emsp;`glInvalidateFramebuffer`（OpenGL ES 3.0）的语义是：应用声明指定附件的内容此后不再需要，GL 实现可以自由丢弃。Khronos 的 `ARB_invalidate_subdata` 规范明确指出，其目的是让实现**避免不必要的数据传输**，并特别指出分块渲染器是主要受益者。

&emsp;&emsp;代码示例 1 是一个延迟着色管线中的典型用法：几何通道写 G-Buffer，光照通道读 G-Buffer。几何通道结束后，深度附件不再需要；光照通道结束后，G-Buffer 的颜色附件也不再需要。在这两个时刻分别失效，可以省掉对应的 Tile→DRAM 写回。

```c
/* 代码示例 1：延迟着色管线中的帧缓冲失效（OpenGL ES 3.0） */

/* --- 几何通道：写入 G-Buffer --- */
glBindFramebuffer(GL_FRAMEBUFFER, gbufferFBO);
glDrawBuffers(3, gbufferDrawBuffers);
/* ... 绘制场景几何体 ... */

/* 几何通道结束：深度附件此后不再被读取 */
GLenum geomAttachments[] = { GL_DEPTH_ATTACHMENT };
glInvalidateFramebuffer(GL_FRAMEBUFFER, 1, geomAttachments);

/* --- 光照通道：读取 G-Buffer，输出到默认帧缓冲 --- */
glBindFramebuffer(GL_FRAMEBUFFER, 0);
/* ... 绑定 G-Buffer 纹理并绘制全屏光照 pass ... */

/* 光照通道结束：G-Buffer 颜色附件不再需要 */
GLenum lightAttachments[] = {
    GL_COLOR_ATTACHMENT0,
    GL_COLOR_ATTACHMENT1,
    GL_COLOR_ATTACHMENT2
};
glBindFramebuffer(GL_FRAMEBUFFER, gbufferFBO);
glInvalidateFramebuffer(GL_FRAMEBUFFER, 3, lightAttachments);
```

&emsp;&emsp;这里最容易踩的坑是**时序**。失效要在数据确实死亡之后、下一次有效写入之前发出。在绘制**之前**失效颜色附件，等于声明旧内容无关紧要（消除加载）；在绘制**之后**立即失效，会丢弃刚渲染的结果，画面可能闪烁或变黑。两种用法对应两种目的：**写前失效消加载，读后失效消存储**。

&emsp;&emsp;另一个常见混淆是把失效和 `glClear` 当成一回事。两者在性能层面有相似之处，但语义不同：`glClear` 主动写入一个已知值；失效只是声明旧数据无关紧要，不保证任何具体内容。需要确定状态（比如纯黑背景）时用 `glClear`；只是要覆盖、不关心覆盖前状态时，失效更轻量。


### 3.2 Vulkan：把提示写进渲染通道定义

&emsp;&emsp;Vulkan 把同一件事从运行时调用变成了渲染通道创建时的静态属性。每个附件描述里的 `loadOp` 和 `storeOp` 分别控制通道开始和结束时对内存的操作：

- `VK_ATTACHMENT_LOAD_OP_DONT_CARE`：开始时不需要加载已有内容；
- `VK_ATTACHMENT_STORE_OP_DONT_CARE`：结束时不需要把结果写回内存。

&emsp;&emsp;ImgTec 的文档用一句话概括 `DONT_CARE`：“整个场景反正都会被完整渲染，不要加载它。”同一份文档还给了个强硬但准确的建议：除非你绝对确定需要保留内容，否则不要用 `PRESERVE`，因为它会引入一次完整的主存往返。

&emsp;&emsp;代码示例 2 是与示例 1 等价语义的 Vulkan 表达。注意失效意图不再出现在命令流里，而是编码在 `VkAttachmentDescription` 中。

```c
/* 代码示例 2：Vulkan 渲染通道附件描述中的生命周期声明 */

VkAttachmentDescription attachments[4];

/* 颜色附件 0-2：G-Buffer，通道开始无需加载旧内容，
   通道结束需要保留供光照通道读取 */
for (int i = 0; i < 3; ++i) {
    attachments[i].format         = VK_FORMAT_R16G16B16A16_SFLOAT;
    attachments[i].samples        = VK_SAMPLE_COUNT_1_BIT;
    attachments[i].loadOp         = VK_ATTACHMENT_LOAD_OP_DONT_CARE; /* 消加载 */
    attachments[i].storeOp        = VK_ATTACHMENT_STORE_OP_STORE;
    attachments[i].stencilLoadOp  = VK_ATTACHMENT_LOAD_OP_DONT_CARE;
    attachments[i].stencilStoreOp = VK_ATTACHMENT_STORE_OP_DONT_CARE;
    attachments[i].initialLayout  = VK_IMAGE_LAYOUT_UNDEFINED;
    attachments[i].finalLayout    = VK_IMAGE_LAYOUT_SHADER_READ_ONLY_OPTIMAL;
}

/* 深度附件：几何通道内部使用，结束后不再被读取。
   storeOp = DONT_CARE 直接消除 Tile→DRAM 写回 */
attachments[3].format         = VK_FORMAT_D32_SFLOAT;
attachments[3].samples        = VK_SAMPLE_COUNT_1_BIT;
attachments[3].loadOp         = VK_ATTACHMENT_LOAD_OP_CLEAR;
attachments[3].storeOp        = VK_ATTACHMENT_STORE_OP_DONT_CARE; /* 消存储 */
attachments[3].stencilLoadOp  = VK_ATTACHMENT_LOAD_OP_DONT_CARE;
attachments[3].stencilStoreOp = VK_ATTACHMENT_STORE_OP_DONT_CARE;
attachments[3].initialLayout  = VK_IMAGE_LAYOUT_UNDEFINED;
attachments[3].finalLayout    = VK_IMAGE_LAYOUT_DEPTH_STENCIL_ATTACHMENT_OPTIMAL;
```

&emsp;&emsp;从实用角度看，Vulkan 这个设计的好处是**不容易忘**：生命周期在创建通道时就写死了，不需要每帧在某个时刻记得发一条指令。代价是灵活性降低，运行时无法改变主意。


### 3.3 CUDA UVM：消除冗余内存迁移

&emsp;&emsp;CUDA 的统一虚拟内存（UVM）让 CPU 和 GPU 共享地址空间，系统按需自动迁移数据。方便，但也会搬一些实际上不会再被读的数据。Zhu 等人在 2022 年的 IISWC 论文里把这类搬运叫**冗余内存迁移**：缓冲区被迁到 GPU 后，在被读取之前就被完整覆盖，这次迁移对结果毫无贡献。

&emsp;&emsp;解决思路和帧缓冲失效一样：应用告诉驱动“这段内容死了，别迁”。CUDA Runtime API 里有 `cudaMemDiscardAndPrefetchBatchAsync`，语义上等价于分别调用丢弃和预取，但批处理给了驱动更大的调度自由度。

&emsp;&emsp;代码示例 3 是一个迭代式 GPU 计算的典型模式：缓冲区每轮开始被完整覆写，所以上一轮的内容在被覆盖前不需要迁回主机。

```cuda
/* 代码示例 3：CUDA UVM 中利用丢弃指令消除冗余迁移 */

float *d_buffer;
size_t numBytes = N * sizeof(float);
cudaMallocManaged(&d_buffer, numBytes);

for (int iter = 0; iter < NUM_ITERS; ++iter) {
    /* 本轮会完整覆写缓冲区，上一轮内容无需迁回主机 */
    if (iter > 0) {
        cudaMemDiscardAndPrefetchBatchAsync(
            (void **)&d_buffer,
            &numBytes,
            1,
            cudaMemPrefetchToDevice);
    }

    computeKernel<<<grid, block>>>(d_buffer, N);
    cudaDeviceSynchronize();
}
```

&emsp;&emsp;论文里的量化结果值得贴出来：在一个 GPU 内存超配的大型深度学习应用中，丢弃指令把训练吞吐量提升了 **61.2%**；在一个数据量为 GPU 内存两倍的 GPU 数据库应用中，消除了 **85.8%** 的内存传输，加速 **4.17 倍**。这说明“数据已死”这条信息在图形之外同样值钱。


### 3.4 CPU：缓存层次结构里的同类操作

&emsp;&emsp;CPU 侧没有一条叫 `discard` 的单一指令，但同一原则在 ARM 和 x86 上以不同形态存在。

&emsp;&emsp;**非临时存储** 是最直接的对应。一次普通存储不是纯写：CPU 通常要先把目标缓存行从内存读进缓存（读所有权，RFO），再改其中一部分。对于写完短期不再读的流式数据，这次读取毫无意义。非临时存储绕过缓存层次，把完整缓存行直接送进写合并缓冲区下发主存，**省掉 RFO 读**，同时避免一次性数据污染热缓存。代码示例 4 是 x86 上的典型形态：用 `_mm_stream_si128` 写完整 128 位缓存行，最后 `_mm_sfence` 保证可见性。

```c
/* 代码示例 4：x86 非临时存储写入流式数据 */

#include <emmintrin.h>

void streaming_write(float *dst, size_t count) {
    /* 假定 dst 按 16 字节对齐，count 为 16 字节块的整数倍 */
    __m128i value = _mm_set1_epi32(0);
    for (size_t i = 0; i < count; i += 4) {  /* 4 float = 16 字节 */
        _mm_stream_si128((__m128i *)(dst + i), value);
    }
    _mm_sfence();
}
```

&emsp;&emsp;**缓存行无效化** 从“不写回”的方向做减法。ARM 架构提供了 `DC IVAC`（Data Cache Invalidate by VA to Point of Coherency）：它使指定虚拟地址对应的缓存行无效，且**不将脏数据写回内存**——这与帧缓冲失效“不再保留”的语义直接对应。相比之下，x86 用户态没有纯“无效不写回”的通用指令（`INVD` 是特权指令且会破坏内存一致性），`CLFLUSH`/`CLFLUSHOPT` 执行的是“写回并无效”，`CLDEMOTE` 则是把缓存行降级到更远层级而非丢弃。这一差异本身说明：同一原则在不同 ISA 上的暴露程度不同，x86 更倾向于用非临时存储从“写”的一侧避免冗余搬运，ARM 则同时提供了从“无效”一侧做减法的指令。代码示例 5 给出 ARM 上的概念性调用形态。

```c
/* 代码示例 5：ARM DC IVAC —— 使缓存行无效且不写回 */

/* DC IVAC, <Xt>：按虚拟地址使数据缓存行无效至一致性点。
   脏数据被丢弃而非写回内存，适用于已确定内容不再需要的缓冲区。 */
static inline void dc_ivac(const void *addr) {
    uint64_t va = (uint64_t)addr;
    asm volatile("dc ivac, %0" : : "r"(va) : "memory");
}
```

&emsp;&emsp;操作系统层面的**写时复制**是另一种惰性策略：`fork()` 不立即复制地址空间，只在某一方真正写入某页时才复制。从未被写入的页自始至终没被复制过——这等于把“是否需要”这个问题延迟到写入发生才回答。


## 4. 放在一起看：共同点与边界

&emsp;&emsp;把四层机制并排，能看出一条共同的逻辑：**系统默认保守地“保留/加载/迁移”；应用把“数据已死”的信息递过去，系统据此跳过本应发生的搬运。**

| 层级 | 机制 | 消掉的搬运 | 信息给的时机 | 示例 |
|---|---|---|---|---|
| OpenGL | `glInvalidateFramebuffer` | DRAM→Tile 加载或 Tile→DRAM 写回 | 运行时命令流中 | 示例 1 |
| Vulkan | `loadOp`/`storeOp = DONT_CARE` | 同上 | 渲染通道创建时 | 示例 2 |
| CUDA UVM | 丢弃指令 / `cudaMemDiscard*` | 冗余主机↔设备迁移 | 运行时，覆盖之前 | 示例 3 |
| CPU | 非临时存储 / 缓存无效化（ARM `DC IVAC`） | RFO 读或脏行写回 | 指令级 | 示例 4、5 |

&emsp;&emsp;有一个值得注意的演进方向：**从运行时提示往静态声明走**。OpenGL 是命令流里的一次调用，Vulkan 把它前移到管线状态，驱动可以在更高层做全局规划。CUDA 的批处理接口也是类似思路，把逐条丢弃打包，给驱动更多调度空间。

&emsp;&emsp;但这类优化不是无条件的。三条边界值得记住：

&emsp;&emsp;**第一，信息必须正确。** 对一个后续还要读的附件发 `STORE_OP_DONT_CARE`，结果就是数据损坏。ImgTec 的警告反过来说也成立：只有你确定“不需要保留”时，保留操作才是多余的。

&emsp;&emsp;**第二，收益是架构相关的。** `ARB_invalidate_subdata` 规范自己就说，GL 实现是否利用这条知识取决于实现，分块渲染器是主要受益者。桌面立即模式 GPU 上同一调用的收益可能远不如 TBR 明显。CPU 侧同样如此：x86 的非临时存储要求对齐、顺序、完整缓存行写入，代码示例 4 的结构就是在满足这个前提；ARM 的 `DC IVAC` 则是平台相关的维护操作，使用前需确认目标架构与特权级。

&emsp;&emsp;**第三，时序比 API 本身更容易出错。** 帧缓冲失效在绘制前还是绘制后，语义完全不同；Vulkan 的 `storeOp` 在通道创建时定死；CUDA 的丢弃要在数据死后、下次使用前发出。判断依据始终是数据的实际生命周期，而不是“听说这个 API 能优化”。


## 5. 结语

&emsp;&emsp;`glInvalidateFramebuffer` 不是一个孤立的技巧。从移动 GPU 的 Tile Buffer，到 Vulkan 的附件操作，到 CUDA 统一内存的迁移决策，再到 CPU 的缓存行，同一件事反复出现：**知道什么数据可以不管，往往比让数据动得更快更能解决问题。** 上面五个代码示例对应五个抽象层级，但核心只有一句话——数据已经死了，就别再为它付运费。
