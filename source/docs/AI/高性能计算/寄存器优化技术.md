# GPU Kernel 寄存器优化：从占用率权衡到架构级重分配

&emsp;&emsp;**摘要**：寄存器是 GPU 上速度最快的存储，却也是决定内核占用率的最稀缺资源。一个内核每线程多用 1 个寄存器，在分配粒度的“悬崖效应”下，SM 活跃 warp 数可能从 64 直接腰斩至 32。然而，寄存器优化的目标从来不是“用得越少越好”——FlashAttention、cuBLAS、CUTLASS 等高性能内核恰恰通过刻意维持高寄存器用量、以指令级并行取代 warp 切换来隐藏延迟。本文以这一核心张力为主线，建立寄存器压力与占用率的量化模型，梳理从源码重构、编译指示、溢出重定向到架构级动态重分配的分层技术，并给出诊断流程、实验设计与检查清单。第 7 节在 RTX 3050（sm_86）上对 H1–H3 做了实测：K2 的 64 累加器版本在 76 regs/50% occupancy 处出现 70% 时长跳升；K3 的 `maxrregcount` 扫描显示 96→80 的 spill 悬崖比 occupancy 阶跃更陡；原生共享溢出与 `setmaxnreg` 受 CUDA 13/Hopper 限制，分别以代理和 N/A 标注。

## 1. 问题背景：寄存器为什么是“第一约束”

&emsp;&emsp;寄存器访问延迟低于 5 个时钟周期，而寄存器溢出的默认去处——本地内存——需经 L2 访问 DRAM，延迟可达 200–400 周期。但寄存器容量极度受限：Ampere 每个 SM 仅 65,536 个 32-bit 寄存器，最多驻留 2,048 线程。满占用率下，每线程平均只有 32 个寄存器可用。

![](https://cdn.jsdelivr.net/gh/grayondream/MyImageBlob@main/imgs/deepseek_svg_20261111_ad29e3.svg)

&emsp;&emsp;更关键的是，寄存器分配并非线性影响占用率，而是以 warp 为粒度向上取整。32 寄存器/线程时每 warp 恰好 1,024 寄存器，可驻留 64 warp；一旦升至 63，每 warp 需 2,016 寄存器、被取整至 2,048，SM 只能容纳 32 warp，占用率直接跌至 50%。实际 GEMM 移植中曾出现寄存器从 128 增至 129、warp 占用率从 33.3% 骤降至 16.7% 的案例。

![](https://cdn.jsdelivr.net/gh/grayondream/MyImageBlob@main/imgs/deepseek_svg_20261111_1b0a55.svg)

&emsp;&emsp;但占用率本身并非目标。高寄存器内核可以在单个 warp 内维持大量独立指令流，通过指令级并行（ILP）而非 warp 切换来掩盖延迟。寄存器优化的真正命题是：**在内核的实际延迟隐藏需求下，找到寄存器用量、占用率与溢出代价之间的帕累托最优点**。

## 2. 性能模型：PRP 与 APRP

&emsp;&emsp;**峰值寄存器压力（PRP）** 定义为指令调度中活跃变量数量在任意程序点的最大值。两个内核可能编译出相同的静态寄存器数，但一个的 PRP 峰值出现在热循环体内，另一个出现在冷路径上，优化优先级截然不同。静态分析工具（如 cuxray）可从 SASS 的 live range 信息重建压力曲线，并映射回源码行号。

![](https://cdn.jsdelivr.net/gh/grayondream/MyImageBlob@main/imgs/deepseek_svg_20261111_48f3bd.svg)

&emsp;&emsp;**调整后峰值寄存器压力（APRP）** 将 PRP 映射到其所属“占用率等价类”的上界：只有当优化将 PRP 推过分配粒度的悬崖时，才会真正改变占用率。在悬崖内部做微小节省，对占用率没有贡献，反而可能因重物化开销拖慢内核。APRP 因此为“值不值得省这几个寄存器”提供了判据。

## 3. 分层优化技术

### 3.1 源码级：缩短活跃区间

&emsp;&emsp;寄存器压力的根源是变量的**活跃区间**过长。核心操作是“缩短活跃区间”：计算推迟到使用点附近，及时释放不再需要的值，并允许编译器对廉价表达式**重物化**（以计算换寄存器）。

![](https://cdn.jsdelivr.net/gh/grayondream/MyImageBlob@main/imgs/deepseek_svg_20261111_eed709.svg)

&emsp;&emsp;典型改造是将“先全部计算、再全部使用”改为“流式计算、即算即用”。多个中间缓冲区同时存活必然触发大量溢出；重构为逐元素流水线后，PRP 可从 O(N) 降至 O(1)。

### 3.2 编译指示：launch bounds 与展开控制

&emsp;&emsp;`__launch_bounds__(maxThreadsPerBlock, minBlocksPerMultiprocessor)` 是向编译器传递占用率意图的主要手段：第二个参数告知编译器“至少希望每 SM 驻留多少 block”，编译器据此反推每线程寄存器上限。它也可能导致更低效的指令序列或溢出，应作为**在 profile 指导下验证的假设**使用，而非无条件开关。

&emsp;&emsp;循环展开因子越大，ILP 潜力越大，但活跃变量也成比例增长。对寄存器敏感的内核应使用 `#pragma unroll 1` 禁止热循环自动展开，或使用小因子在 ILP 与压力之间折中。Triton 中通过 `num_warps`、`num_stages` autotuning 控制有效寄存器负载，是同一思路的体现。

### 3.3 溢出目的地：从本地内存到共享内存

&emsp;&emsp;寄存器需求超出容量时编译器必须溢出。传统 nvcc 默认写入**本地内存**（片外 DRAM 中的线程私有空间）；即便 L1 能吸收部分开销，溢出写仍污染 L2。

&emsp;&emsp;一条重要的替代路径是将溢出重定向到**共享内存**。学术工作 RegDem 通过 SASS 级变换取得几何平均 7%、最高 18% 的加速。NVIDIA 在 CUDA 13.0 中将这一思想产品化：内核定义处添加 `.pragma enable_smem_spilling`，PTXAS 会优先将高成本溢出数据放入共享内存，不足时回退到本地内存。官方基准中该优化使内核时长从 8.35 μs 降至 7.71 μs（降幅 7.76%）。适用信号：存在非零本地内存溢出流量，且共享内存有未被 launch bounds 或 tile 尺寸锁死的余量。

### 3.4 架构级：warp specialization 与 setmaxnreg

&emsp;&emsp;前述技术都在“所有 warp 共享同一寄存器预算”的框架内做文章。Hopper 及后续架构引入的 `setmaxnreg` 指令打破这一前提：同一 CTA 内不同 warpgroup 可在运行时动态调整各自的每线程寄存器配额。轻量角色（TMA 加载的 Producer）释放寄存器，重量角色（WGMMA 的 Consumer）获取这些寄存器。

![](https://cdn.jsdelivr.net/gh/grayondream/MyImageBlob@main/imgs/deepseek_svg_20261111_ea6843.svg)

&emsp;&emsp;这一机制的意义不在于“降低总寄存器用量”，而在于**将寄存器分配到真正需要它们的地方**。在 CUTLASS 3.x 的 Hopper GEMM 中，Producer 只需少量寄存器做地址运算，Consumer 需要大尺寸累加器 fragment；若不进行角色化分配，要么 Consumer 溢出，要么整体占用率被 Producer 的闲置配额拖累。需强调 `setmaxnreg` 是**架构相关**的：需要 Hopper 或更新架构，且受 `__launch_bounds__` 第二参数约束——缺少 `.minctapersm` 信息时 PTXAS 可能静默丢弃该指令。

&emsp;&emsp;**第一步，编译期画像**：`nvcc --ptxas-options=-v` 给出每内核寄存器数、溢出字节数与本地内存用量；`cuxray report` 进一步将溢出指令归因到源码行，报告占用率限制因子与距下一悬崖的差值。

&emsp;&emsp;**第二步，运行时验证**：Nsight Compute 的 Memory Workload Analysis 出现非零 Local Memory Load/Store，且 Occupancy 节标注 “Block Limit Registers”，则寄存器确为限制因子。若溢出为零但占用率仍受寄存器限制，问题在“用得多但没溢出”，此时应评估高寄存器用量换来的 ILP 是否足以补偿占用率损失。

&emsp;&emsp;**第三步，扫描寄存器上限**：遍历 `-maxrregcount` 阶梯，记录每个上限下的溢出字节、blocks/SM 与实测时长，标记帕累托最优点。

&emsp;&emsp;**第四步，做决策**：占用率极低（约 10%）时提升至 30% 往往收益显著；已较高（如 60%）时继续推向 80% 的边际收益可能很小甚至为负。高寄存器内核通过 ILP 隐藏延迟的能力，在计算密集型负载中尤为有效；内存受限负载则仍需更高占用率来容纳并发内存请求。

## 5. 检查清单

&emsp;&emsp;下表汇总各层级的操作与适用信号：

| 层级 | 操作 | 适用信号 |
|---|---|---|
| 源码 | 缩短活跃区间；流式处理替代批量缓冲 | PRP 峰值出现在热循环体内 |
| 源码 | 允许廉价表达式的重物化 | 溢出非零，且重算成本低于访存 |
| 编译指示 | `__launch_bounds__(T, B)` | 占用率受寄存器限制，已知目标 block 数 |
| 编译指示 | `#pragma unroll 1` 或小因子展开 | 自动展开导致寄存器压力越级 |
| 溢出 | CUDA 13.0 `enable_smem_spilling` | 存在本地溢出，共享内存有余量 |
| 架构 | warp specialization + `setmaxnreg`（Hopper+） | warpgroup 寄存器需求悬殊 |
| 工具 | 扫描 `-maxrregcount`，取帕累托前沿 | 任何寄存器受限内核的最终校准 |
| 决策 | 先定位 spill onset，再评估 occupancy；spill-heavy 时不要盲目提高占用率 | `maxrregcount` 扫描出现时长数量级跳变 |

## 6. 实验设计

&emsp;&emsp;实验围绕 PRP/APRP 模型与分层技术展开，检验三个假设：

- **H1（悬崖效应）** ：寄存器用量的性能影响集中体现在跨越占用率“悬崖”时；等价类内部压缩寄存器用量对时长无显著影响，甚至可能因重物化轻微变慢。
- **H2（溢出目的地）** ：共享内存重定向的收益与溢出流量、共享内存余量正相关；溢出为零时收益应为零，验证其适用信号。
- **H3（延迟隐藏路径）** ：计算密集型内核中，高寄存器用量换取 ILP 可在远低于满占用率的 warp 数下达到甚至优于高占用率版本；内存受限内核中该效应不成立。

|---|:---:|:---:|:---:|:---:|
| K1 逐元素向量 | — | — | ✓（阴性对照） | — |
| K2 流式归约 | ✓ | — | ✓ | — |
| K3 分块 GEMM | — | ✓ | — | — |
| K4 WS-GEMM | — | — | — | ✓（本机 N/A） |

&emsp;&emsp;Block C 的原生 C1 需要 CUDA 13.0、Block D 的 `setmaxnreg` 需要 Hopper；本机实际执行范围是 K2 的 C0/C1-manual、K1 阴性对照，以及 A/B 的其余变体。C1-native 与 D 的 N/A 原因见第 7.1、7.6、7.7 节。

&emsp;&emsp;**Block A（源码级，K2）** ：对比 A0（循环外声明中间缓冲区，B 条独立累加链）与 A1（流式重构，单累加链），在 B ∈ {1, 4, 16, 32, 64} 五个压力点测量；32 是实测补充点，用来分辨 83.3% 与 50% 两档 occupancy。

&emsp;&emsp;**Block B（编译指示，K3）** ：B0 无 launch bounds；B1 `__launch_bounds__(256, 2)`；B2 在 B1 基础上对热循环施加 `#pragma unroll 1`；B1-128 使用文档原式的 `__launch_bounds__(128, 2)` 以复核 128 线程配置；low-reg 4×4 作为 H3 的高占用率对照。

&emsp;&emsp;**Block C（共享溢出，K2 高 B / K1 阴性对照）** ：C0 默认本地内存溢出；C1 原生 `.pragma enable_smem_spilling` 需要 CUDA 13.0，本机 12.4 不可用；实测用 C1-manual（`__shared__` 暂存）作为代理。K1 的 local bytes 为 0，作为“无溢出可重定向”的阴性对照。

&emsp;&emsp;**Block D（架构级，K4，Hopper+）** ：D0 warp specialization 但寄存器均分；D1 Producer dealloc 至 40 registers、Consumer alloc 至 232 registers。编译配置须包含显式 `minBlocksPerMultiprocessor`，否则 PTXAS 可能静默丢弃 `setmaxnreg`。

&emsp;&emsp;每个变体用 `ptxas -v` 与 `cuobjdump --dump-resource-usage` 记录寄存器/溢出，用 `cudaFuncGetAttributes` 与 `cudaOccupancyMaxActiveBlocksPerMultiprocessor` 读取运行时资源，用 CUDA event 计时。每变体预热 10 次、正式 50 次，重复 3 轮并交错执行；计时前运行 15 s burn-in 以稳定时钟。`cuxray` 未安装，Nsight Compute 因 `ERR_NVGPUCTRPERM` 不可用，因此第 7 节不报告 PRP 曲线、L1 命中率或本地内存硬件计数器。

## 7. 实测：RTX 3050 上的寄存器悬崖、launch bounds 与溢出路径

### 7.1 环境、方法与限制

&emsp;&emsp;测试平台为 NVIDIA GeForce RTX 3050（GA106，`sm_86`，20 个 SM，1536 threads/SM，65536 regs/SM，100 KB smem/SM，1.5 MB L2，8 GB GDDR6），驱动 595.99.02，CUDA Toolkit 12.4，`nvcc` 12.4.131，host compiler 为 `g++-13.4`。GPU 动态调频无法锁定；正式测量前先运行 15 s 的 FMA burn-in，使 SM 时钟稳定在 1935 MHz。实验开始与结束时 `nvidia-smi` 均记录到 1935 MHz / 7001 MHz，实验前后温度记录为 50 °C 与 46 °C，因此表中的差异不是冷启动升频造成的。

&emsp;&emsp;与第 1 节引用的 A100 示例不同，RTX 3050 每个 SM 最多驻留 1536 个线程（48 warp），满占用率下每线程平均只有 65536 / 1536 ≈ 42.7 个寄存器；寄存器分配仍以 256 个/warp 为粒度。下文所有 occupancy 都按 1536 threads/SM 计算，而不是按 2048 threads/SM 计算。这个差异会改变“悬崖”的位置：在 64 warp 的 GPU 上，32→33 regs 就可能腰斩 occupancy；在 48 warp 的 RTX 3050 上，第一处明显下降出现在约 40→41 regs，之后是 64→65、96→97 等位置。

&emsp;&emsp;每个变体预热 10 次、测量 50 次，重复 3 轮；不同变体在轮次之间交错执行，而不是把一个变体连续跑完。表中 median 是 150 个样本的中位数，p99 是同一批样本的 99 分位。所有计时变体都先与 CPU 参考实现比对：K1/K2 检查 1M 个输出，K3 检查 256×256 GEMM 的最大绝对误差（实测 5.7×10⁻⁶），全部 `correct=true`。计时使用 CUDA event 包住单次 launch，50 次连续入队后统一同步读取；K3 主表用 N=2048，寄存器上限扫描用 N=1024，以限制 spill-heavy 配置的运行时间，两者的绝对 GFLOP/s 不可直接横比。

&emsp;&emsp;三项工具限制必须明确。第一，本机 `nvcc` 12.4 的 `ptxas` 不接受 `.pragma enable_smem_spilling`（该特性从 CUDA 13.0 才引入），因此 Block C 的**原生 C1 未测**；第 7.6 节的 C1-manual 是 `__shared__` 暂存代理，不是原生特性。第二，`setmaxnreg` 需要 `sm_90+`，本机 `sm_86` 无法执行 Block D，表中标为 N/A。第三，Nsight Compute 因 `ERR_NVGPUCTRPERM` 不能读取硬件计数器，`cuxray` 未安装，因此本节不报告 PRP 曲线、L1 命中率或本地内存硬件计数器；这些量一律标为“未测”，不用别的指标替代推断。

&emsp;&emsp;第一个结论是：**文档中的 `__launch_bounds__(128, 2)` 在这颗 GPU 上不是有效约束。** 寄存器预算为 65536 / (128 × 2) = 256 regs/thread，而内核自然用量是 128 regs，因此 B1-128 的寄存器数没有变化；它只是把 block 从 256 线程改成 128 线程，仍只驻留 4 个 block、512 个线程（33.3% occupancy），但 128×64 的 tile 复用更少，时长反而从 13.499 ms 升到 17.469 ms（+29%）。B1 `(256,2)` 的预算正好是 128 regs，与自然用量相等，所以也没有约束，B0/B1 的 13.499/13.486 ms 实质相同。

&emsp;&emsp;第二个结论是 APRP 的一个正面例子：B2 把内层 `#pragma unroll 1` 后，寄存器从 128 降到 96，但 96 × 256 × 3 = 73728 > 65536，第三个 block 仍然放不下，occupancy 保持 33.3%；时长反而从 13.499 ms 升到 14.607 ms（+8.2%）。这就是“在同一个 occupancy 等价类内部压缩寄存器”的典型代价：没有换来更多 warp，却损失了 ILP。

&emsp;&emsp;第三个结论是：Low-reg 4×4 用 58 regs 换到 4 个 block、66.7% occupancy，时长 11.807 ms，比 B0 快 12.5%，GFLOP/s 从 1272.6 升到 1455.1。这个结果与 H3 的“计算密集型内核可以靠高寄存器 ILP 击败高占用率”相反，原因在 7.5 节展开。

### 7.5 H3：ILP 与 occupancy 的边界

&emsp;&emsp;H3 把“计算密集”与“内存受限”当成两种延迟隐藏路径。表 7-6 与图 11 的 K1 部分给出内存受限侧：K1 每线程只有 12 regs，通过动态共享内存把 occupancy 人为压到 66.7%、33.3%、16.7%。100%→66.7% 时带宽只从 117.4 降到 114.7 GB/s（−2%），说明这个内核在约 2/3 occupancy 时已经接近饱和；33.3% 时降到 100.8 GB/s（−14%），16.7% 时降到 64.9 GB/s（−45%）。因此“内存受限内核需要更高 occupancy”只在低占用率区间成立，不能外推成“越高越好”。

### 7.6 Block C：本地溢出 vs 手工共享内存暂存

&emsp;&emsp;两个结果都反直觉。第一，C0 在 83.3% occupancy 下比 33.3% 下慢 90%（18.591 vs 9.763 ms）：更多并发线程意味着更多本地内存栈同时活跃，L1/L2 与本地内存带宽被争用，和 7.4 节 cap 80 的现象一致。第二，在相同的 2 block/SM、33.3% occupancy 下，C1-manual 的 3.815 ms 比 C0 的 9.763 ms 快 2.56 倍。也就是说，**在溢出流量非零时，把溢出目的地从本地内存换到共享内存，即使牺牲了 occupancy，净收益仍然可以为正**。这支持 H2 的方向，也说明“先看 spill bytes、再看 occupancy”的顺序是对的。

### 7.8 对诊断流程与检查清单的修正

&emsp;&emsp;把第 7.2–7.6 节压缩成可操作判据，可以给第 4 节的诊断流程补三条：

- **先找 spill onset，再谈 occupancy。** `-maxrregcount` 扫描中，时长数量级跳变出现在 local bytes 从 0 变正、并继续增长的位置（本机 96→80），而不是 occupancy 阶跃本身。APRP 应把 spill bytes/local traffic 作为与 occupancy 并列的维度。
- **`__launch_bounds__(T,B)` 只有在隐含预算 `65536/(T×B)` 低于自然寄存器用量时才是约束。** 本机 `(128,2)` 允许 256 regs，对 128-reg 内核完全无效；`(256,2)` 正好等于自然用量，也无效。实际校准应使用 `-maxrregcount` 扫描，而不是只看 launch bounds 参数。
- **spill-heavy 内核不要盲目提高 occupancy。** C0 的 5 block/SM 比 2 block/SM 慢 90%，cap 80 比 cap 96 慢 5.4 倍；更多并发线程会放大本地内存争用。对这类内核，降低并发、把溢出搬到片上，往往比堆 warp 更有效。

&emsp;&emsp;第 5 节检查清单因此补了一行决策项：先定位 spill onset，再评估 occupancy；spill-heavy 时不要盲目提高占用率，适用信号是 `maxrregcount` 扫描出现时长数量级跳变。

&emsp;&emsp;H1–H3 的最终判读如下。H1：**支持，但悬崖在 spill/occupancy 的组合处**；A0 只在 B=64 跨过 50% occupancy 时出现 70% 跳升，B=16→32 的类内变化只有 2%。H2：**方向支持，原生特性未测**；等 occupancy 下 C1-manual 比本地溢出快 2.56×，但原生 `.pragma enable_smem_spilling` 需要 CUDA 13，本机不能验证。H3：**分裂**；K1 的内存受限侧在低 occupancy 时变慢，K3 的计算密集侧反而是低寄存器/高 occupancy 版本快 12.5%，不支持“高寄存器 ILP 普遍胜出”的强表述。

### 7.9 复现与关键代码

&emsp;&emsp;代码清单 1 是 K2 的 A0/A1 核心；两者对所有 B 执行相同的 FMA 数量，区别只在累加器是否同时存活。

```cuda
// src/bench_k2_a.cu（节选）
template <int B>
__global__ void k2_a0(const float* in, float* out, size_t n) {
  float acc[B];                       // B 条独立累加链，全部同时存活
#pragma unroll
  for (int j = 0; j < B; ++j) acc[j] = 0.0f;
  size_t i = (size_t)blockIdx.x * blockDim.x + threadIdx.x;
  size_t stride = (size_t)gridDim.x * blockDim.x;
  for (; i < n; i += stride) {
    float v = in[i];
#pragma unroll
    for (int j = 0; j < B; ++j) acc[j] += v * float(j + 1);
  }
  float s = 0.0f;
#pragma unroll
  for (int j = 0; j < B; ++j) s += acc[j];
  out[(size_t)blockIdx.x * blockDim.x + threadIdx.x] = s;
}

template <int B>
__global__ void k2_a1(const float* in, float* out, size_t n) {
  float s = 0.0f;                     // 单条链，寄存器压力与 B 基本无关
  size_t i = (size_t)blockIdx.x * blockDim.x + threadIdx.x;
  size_t stride = (size_t)gridDim.x * blockDim.x;
  for (; i < n; i += stride) {
    float v = in[i];
#pragma unroll
    for (int j = 0; j < B; ++j) s += v * float(j + 1);
  }
  out[(size_t)blockIdx.x * blockDim.x + threadIdx.x] = s;
}
```

}

## 8. 结语

&emsp;&emsp;第 7 节的实测把上述框架压缩成三个可操作判据：先看 spill bytes，再看 occupancy；`__launch_bounds__` 只有在隐含预算低于自然寄存器用量时才是约束；对 spill-heavy 内核，提高占用率可能因本地内存争用而变慢。RTX 3050 上，K2 的 64 累加器版本在 76 regs/50% occupancy 处出现 70% 时长跳升；K3 的 96→80 扫描出现 5.4 倍 spill 悬崖；K1 的内存受限侧与 K3 的计算密集侧对 occupancy 的反应方向相反。这些结果不推翻“ILP 可以替代 occupancy”的可能性，但把它从普遍结论降为一个需要逐内核验证的条件命题。

&emsp;&emsp;寄存器优化的本质是在三个不可兼得的量之间求解：**单线程 ILP 潜力、SM 并发 warp 数、溢出带来的存储层次降级代价**。占用率是中间变量而非目标函数。cuBLAS、FlashAttention 和 CUTLASS 的生产实践已经表明，刻意维持较低占用率、将寄存器集中供给计算密集路径的内核，可以在许多真实负载中击败“高占用率但寄存器饥饿”的版本。优化的起点因此不是“把寄存器省下来”，而是回答一个更精确的问题：**这个内核的延迟是由什么隐藏的——warp 切换，还是指令级并行？** 答案决定了寄存器应当被压缩、被保留，还是被动态重分配。
