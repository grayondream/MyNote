# 深入理解计算机内存——高级缓存实验

>&emsp;&emsp;在《深入理解计算机内存——CPU 缓存实验》中，我们通过指针追逐、带宽、缓存行、伪共享、线程扩展和 TLB 等基础实验，量化了缓存层级、带宽瓶颈与 TLB 代价。本文在此基础上进一步探索更贴近真实编程场景的缓存行为：非临时存储、写合并、数据布局、矩阵乘法优化、缓存冲突与指令缓存压力。所有实验统一采用 **2^4 → 2^30 字节** 的工作集扫描，以曲线形式展示不同配置在各缓存层级边界的行为差异。

> 环境：WSL2.0-Ubuntu
>
> CPU：AMD Ryzen 5 5600X（6 核 12 线程，L1d=32KB/核，L2=512KB/核，L3=32MB，cacheline=64B）

## 1 非临时存储（Non-Temporal Store）

### 1.1 背景

&emsp;&emsp;普通 store 操作会将数据先写入缓存行（标记为"脏"），待缓存行被驱逐时才写回内存。这对于"写完不再读"的大块数据传输来说是浪费——数据占据宝贵的缓存空间，却不会被再次利用。非临时存储（streaming store）通过 `_mm_stream_si128` 等指令绕过缓存，直接将数据写入内存，避免污染缓存。

### 1.2 测试方法

&emsp;&emsp;工作集从 16B 扫描到 1GB（2^4 → 2^30），分别用普通 store 和 streaming store 写入全部元素，测带宽：

```cpp
// Normal store
for (size_t i = 0; i < steps; ++i)
    _mm_store_si128(reinterpret_cast<__m128i*>(dst + i * 16), v);
// Streaming store
for (size_t i = 0; i < steps; ++i)
    _mm_stream_si128(reinterpret_cast<__m128i*>(dst + i * 16), v);
```

### 1.3 结果

![](https://cdn.jsdelivr.net/gh/grayondream/MyImageBlob/imgs/cpu_cache_NTStore.png)

&emsp;&emsp;**曲线分析：**

- **小工作集（< 2^11 = 2KB）**：两者差异不大，因为数据完全在 L1/L2 缓存内，streaming store 的 RFO 省略优势不明显。
- **中等工作集（2^11 ~ 2^15 = 2KB~32KB）**：streaming store 开始领先，因为普通 store 的 RFO（Read-for-Ownership）和缓存污染代价逐渐显现。
- **大工作集（> 2^15 = 32KB，超出 L3）**：streaming store 稳定快 **1.5~2×**（约 12 vs 18 GB/s），因为普通 store 每次写入都要先读旧行、标记脏位、后续驱逐写回；streaming store 直接写内存，省去了这些开销。

### 1.4 注意事项

- Streaming store 只在"写完不再读"时有意义；若后续需要读取这些数据，反而会因为缓存未命中而变慢。
- WSL2 下 streaming store 未必比普通 store 快很多，因为写入仍经缓存子系统。

## 2 写合并（Write Combining）

### 2.1 背景

&emsp;&emsp;现代 CPU 的 store buffer 会尝试将多次部分写入合并成一次完整的 cacheline 写入（write combining），以减少总线事务。但如果程序只写了 cacheline 中的部分字节（如只写 1 个字节），合并机制无法生效，每次写入都要发起一次总线事务，带宽大幅下降。

### 2.2 测试方法

&emsp;&emsp;工作集从 16B 扫描到 1GB，两种写入模式：

- **bad**：4B 部分写（`_mm_storeu_si128`，每次只写 cacheline 的 1/16），无法利用写合并。
- **good**：64B streaming cacheline 填充（4 次 `_mm_stream_si128`，每次 16B = 64B/次），充分利用写合并。

```cpp
// bad: 4-byte partial writes (only 1/16 of cacheline per store)
for (size_t i = 0; i + 16 <= n; i += 4)
    _mm_storeu_si128(dst + i, v);
// good: 64-byte streaming cacheline fills (full cacheline per iteration)
for (size_t i = 0; i + 64 <= n; i += 64) {
    __m128i* p = dst + i;
    _mm_stream_si128(p, v); _mm_stream_si128(p+1, v);
    _mm_stream_si128(p+2, v); _mm_stream_si128(p+3, v);
}
```

### 2.3 结果

![](https://cdn.jsdelivr.net/gh/grayondream/MyImageBlob/imgs/cpu_cache_WriteCombining.png)

&emsp;&emsp;**曲线分析：**

- **小工作集（< 2^9 = 512B）**：两者差异小，store buffer 能有效合并部分写。
- **中等工作集（2^9 ~ 2^13 = 512B~8KB）**：good 开始大幅领先，因为 bad 的 4B 部分写无法利用写合并，每次写入都占一次总线事务。
- **大工作集（> 2^13 = 8KB）**：good 稳定快 **6~7×**（约 4 vs 27 GB/s）。原因：bad 模式每次只写 4B，store buffer 深度有限（通常 48-72 条），无法完全合并，总线利用率极低；good 模式每条 `_mm_stream_si128` 搬运 16B，4 条指令填满一条 cacheline（64B），总线利用率最大化。

### 2.4 注意事项

- 写合并是微架构特性，不同 CPU 实现差异大。
- 部分写（partial write）是严重的性能陷阱——4B 写比 64B cacheline 写慢 6~7 倍。
- 结构体字段未对齐到 cacheline 时容易触发部分写，应尽量让热字段紧凑排列。

## 3 访问模式（Access Pattern）

### 3.1 背景

&emsp;&emsp;矩阵遍历方向对性能的影响是缓存局部性的经典案例。C/C++ 按行优先（row-major）存储，行优先遍历时相邻元素在内存中也是相邻的，能充分利用 cacheline 的空间局部性；列优先遍历时每次跳过整行，远超 cacheline 大小，导致大量 L1 miss。

### 3.2 测试方法

&emsp;&emsp;方阵总字节数从 2^4 扫描到 2^30（N 从 2 到 ~11500），分别按行优先和列优先遍历求和：

```cpp
// Row-major (cache-friendly)
for (size_t i = 0; i < N; ++i)
    for (size_t j = 0; j < N; ++j) sum += mat[i][j];
// Column-major (cache-unfriendly)
for (size_t j = 0; j < N; ++j)
    for (size_t i = 0; i < N; ++i) sum += mat[i][j];
```

### 3.3 结果

![](https://cdn.jsdelivr.net/gh/grayondream/MyImageBlob/imgs/cpu_cache_AccessPattern.png)

&emsp;&emsp;**曲线分析：**

- **小矩阵（< 2^14 = 16KB，L1 内）**：两者差异小，行优先略优但列优先也能命中缓存。
- **中等矩阵（2^14 ~ 2^18 = 16KB~256KB，L2 内）**：列优先劣势显现，每次跳行导致 L1 miss 激增，行优先仍保持高带宽。
- **大矩阵（> 2^18 = 256KB，超出 L2）**：行优先仍维持 **6~8 GB/s**，列优先跌到 **<1 GB/s**，差距达 **7~8×**。

### 3.4 注意事项

- 这个差异与矩阵大小密切相关。若矩阵能完全放入 L2/L3，列优先的劣势会缩小。
- 编译器优化（如循环交换）可能改变实际访问顺序，需用 `volatile` 或累加防止循环消除。

## 4 矩阵乘法（Matrix Multiply）

### 4.1 背景

&emsp;&emsp;矩阵乘法是线性代数的核心运算，也是缓存优化的经典战场。朴素三重循环（naive）的内层循环对两个矩阵的访问模式完全不同，导致大量 cache miss。通过转置（transpose）、分块（blocking）和 SIMD 向量化，可以显著提升性能。

### 4.2 测试方法

&emsp;&emsp;总内存（3 个矩阵）从 2^4 扫描到 2^30，四种实现：

- **naive**：三重循环，`C[i][j] += A[i][k] * B[k][j]`
- **transpose**：转置 B 使内层循环访问连续内存
- **blocked**：分块（tile=32），提高 L1/L2 局部性
- **simd**：AVX2 向量化（256bit，4 个 double 并行）

### 4.3 结果

![](https://cdn.jsdelivr.net/gh/grayondream/MyImageBlob/imgs/cpu_cache_Matmul.png)

&emsp;&emsp;**曲线分析：**

- **小矩阵（< 2^16 = 64KB，L2 内）**：naive 因简单性反而最快（~11 GFLOPS），SIMD 的开销不值得。
- **中等矩阵（2^16 ~ 2^20 = 64KB~1MB，L2~L3）**：blocked 和 simd 开始超越 naive，分块减少 cache miss，SIMD 提升计算密度。
- **大矩阵（> 2^20 = 1MB，超出 L3）**：blocked（tile=32）最优（~8 GFLOPS），naive 跌到 ~3 GFLOPS。SIMD 因转置开销反而不如 blocked。

### 4.4 注意事项

- GFLOPS = 2×N³/cycles，N=512 时峰值约 8 GFLOPS（单精度）。
- 分块大小（tile）需要实验调整，与 L1/L2 容量相关。
- 编译器 `-O3` 可能自动向量化，V4 需显式 intrinsics 以确保 SIMD 生效。

## 5 AoS vs SoA 数据布局

### 5.1 背景

&emsp;&emsp;面向对象编程习惯将同一对象的所有字段放在一起（Array of Structures, AoS），但这种布局对 SIMD 和缓存不友好——遍历"粒子的 x 坐标"时，每次都要跳过 y、z、vx、vy、vz 等字段，加载整条 cacheline 却只用 8B。Structure of Arrays（SoA）将所有粒子的 x 坐标连续存放，遍历时 cacheline 利用率最大化。

### 5.2 测试方法

&emsp;&emsp;粒子数从少到多扫描（总字节数 2^4 → 2^30），遍历所有粒子的 x 坐标：

```cpp
// AoS: 粒子数据交错存储
struct Particle { float x, y, z, vx, vy, vz; int id; };
for (int i = 0; i < N; ++i) sum += particles[i].x;
// SoA: x 坐标连续存储
struct Particles { float x[N], y[N], z[N], vx[N], vy[N], vz[N]; };
for (int i = 0; i < N; ++i) sum += particles.x[i];
```

### 5.3 结果

![](https://cdn.jsdelivr.net/gh/grayondream/MyImageBlob/imgs/cpu_cache_AoS_SoA.png)

&emsp;&emsp;**曲线分析：**

- **小工作集（< 2^8 = 256B，L1 内）**：两者差异小，AoS 的 cacheline 浪费在缓存命中时影响有限。
- **中等工作集（2^8 ~ 2^14 = 256B~16KB，L1 内）**：SoA 开始领先，因为 AoS 每次加载 cacheline（64B）只包含 2-3 个粒子的 x 坐标（每个粒子 28B），空间局部性差。
- **大工作集（> 2^14 = 16KB，超出 L1）**：SoA 稳定快 **2~3×**（约 3 vs 8 GB/s），AoS 的空间局部性劣势完全暴露。AoS 带宽随工作集增大持续下降，而 SoA 保持稳定。

### 5.4 注意事项

- SoA 对 SIMD 更友好，但需要多次遍历不同数组，代码组织更复杂。
- 实际应用中需权衡：如果需要同时访问粒子的所有字段，AoS 可能更合适。
- AoS 的 cacheline 利用率只有 ~14%（4B x / 64B cacheline），SoA 为 100%。

## 6 SIMD 对齐（Alignment）

### 6.1 背景

&emsp;&emsp;SIMD 指令（如 `_mm256_load_pd`）要求内存地址对齐到 32 字节（AVX）或 64 字节（AVX-512）。未对齐的加载（`_mm256_loadu_pd`）在旧 CPU 上有显著惩罚，但在现代 CPU（如 Zen 3）上差异很小——因为未对齐加载会自动拆分成两次对齐加载再合并。

### 6.2 测试方法

&emsp;&emsp;工作集从 16B 扫描到 1GB，分别用对齐和非对齐 SIMD load 遍历求和：

```cpp
// Aligned load
__m256d a = _mm256_load_pd(p + i);
// Unaligned load
__m256d a = _mm256_loadu_pd(p + i);
```

### 6.3 结果

![](https://cdn.jsdelivr.net/gh/grayondream/MyImageBlob/imgs/cpu_cache_Alignment.png)

&emsp;&emsp;**曲线分析：**

- **全范围（2^4 ~ 2^30）**：两条曲线几乎重合，差异 **<5%**。
- **原因**：Zen 3 的未对齐加载开销极低（~1 cycle penalty），且预取器能有效处理跨 cacheline 边界的访问。
- **唯一差异点**：在工作集接近 L3 边界（~32MB）时，unaligned 略有下降，但差异仍很小。

### 6.4 注意事项

- 现代 CPU（Zen 3+）对齐/非对齐差异很小（<5%），不必过度追求对齐。
- 仅在跨 cacheline 边界且工作集超出缓存时差异稍明显，设计数据结构时应避免频繁跨边界访问。

## 7 Cache 冲突（Cache Conflict）

### 7.1 背景

&emsp;&emsp;CPU 缓存使用 set-associative 映射：每个内存地址只能映射到固定数量的 cache set。当多个热数据映射到同一 set 时，会发生容量冲突（capacity conflict），导致频繁驱逐和重载，延迟跳升。stride=4096B 时，所有访问恰好映射到同一 set（因为 4096B 是页大小，也是 set 数量的倍数），触发最严重的冲突。

### 7.2 测试方法

&emsp;&emsp;工作集从 16B 扫描到 1GB，三种步长（stride=64/256/4096B）随机访问，测每访问延迟：

```cpp
for (size_t i = 0; i < accesses; ++i) sink += arr[i * stride];
```

### 7.3 结果

![](https://cdn.jsdelivr.net/gh/grayondream/MyImageBlob/imgs/cpu_cache_CacheConflict.png)

&emsp;&emsp;**曲线分析：**

- **stride=64（蓝色，无冲突）**：延迟在 L1 内（< 2^15 = 32KB）保持 ~4cy，超出后缓存 miss 导致延迟上升。
- **stride=256（橙色，轻微冲突）**：延迟整体高于 stride=64，因为更大的步长降低了预取效率。
- **stride=4096（红色，严重冲突）**：在所有工作集大小上延迟都显著高于其他两者，因为每次访问都映射到同一 set，即使在 L1 内也会产生 set 冲突。延迟从 ~4cy 跳升到 ~10cy，**2.5×** 惩罚。

### 7.4 注意事项

- 不同 CPU 的缓存关联度和 set 数量不同，冲突 stride 位置会变化。
- 这正是 cache-latency 基准中 L2 平台提前爬升的原因——随机 chase 的访问模式天然容易产生 set 冲突。

## 8 指令缓存压力（I-cache Pressure）

### 8.1 背景

&emsp;&emsp;L1i（指令缓存）与 L1d（数据缓存）分开存放。当循环体过大（超出 L1i 容量 32KB）时，指令本身就会频繁 miss，导致取指阶段停顿，IPC（Instructions per Cycle）大幅下降。这在编译器生成的大函数、模板展开、循环展开等场景中容易触发。

### 8.2 测试方法

&emsp;&emsp;编译期模板展开生成不同大小的循环体（代码大小从 2^4 到 2^30 字节），测 IPC：

```cpp
template <size_t N, class F>
struct Unroll {
    static inline void run(F& f) { f(); Unroll<N-1, F>::run(f); }
};
// 使用
for (size_t r = 0; r < reps; ++r)
    Unroll<N, decltype(emit)>::run(emit);
```

### 8.3 结果

![](https://cdn.jsdelivr.net/gh/grayondream/MyImageBlob/imgs/cpu_cache_ICache.png)

&emsp;&emsp;**曲线分析：**

- **小循环体（< 2^12 = 4KB，L1i 内）**：IPC 保持较高（~0.15），指令完全在 L1i 命中。
- **中等循环体（2^12 ~ 2^15 = 4KB~32KB，L1i 边界）**：IPC 开始下降，因为 L1i 容量有限，部分指令需要从 L2 取。
- **大循环体（> 2^15 = 32KB，超出 L1i）**：IPC 跌到 ~0.08，**2×** 惩罚。循环体超出 L1i 容量后，每次循环都要从 L2 甚至 L3 取指，取指阶段成为瓶颈。

### 8.4 注意事项

- 用 `-ftemplate-depth=25000` 编译，确保模板展开成功。
- IPC 反映指令吞吐，不是访存延迟；I-cache miss 导致取指阶段停顿，间接降低整体 IPC。
- 实际应用中，编译器 `-O2`/`-O3` 的循环展开和内联也可能导致 I-cache 压力，需权衡。

## 小结

&emsp;&emsp;八个实验统一采用 2^4 → 2^30 字节的工作集扫描，以曲线形式揭示了缓存与存储子系统的行为规律：

| 实验 | 对比组 | 核心发现 |
|------|--------|----------|
| **非临时存储** | normal vs streaming | 超出 L3 后 streaming 快 1.5~2× |
| **写合并** | bad (4B partial) vs good (64B cacheline) | good 快 6~7×（27 vs 4 GB/s） |
| **访问模式** | row vs column | 超出 L1 后 row 快 7~8× |
| **矩阵乘法** | naive/transpose/blocked/simd | 小矩阵 naive 最优，大矩阵 blocked 最优 |
| **AoS vs SoA** | aos vs soa | SoA 全范围快 2~3×，cacheline 利用率 100% vs 14% |
| **SIMD 对齐** | aligned vs unaligned | 全范围差异 <5% |
| **Cache 冲突** | stride 64/256/4096 | stride=4096 延迟跳升 2.5× |
| **I-cache** | 循环体大小 | 超出 32KB L1i 后 IPC 降 2× |

&emsp;&emsp;把这些结论落到实际编程上，核心原则是：**让数据和指令都具有良好的局部性**。顺序访问、紧凑数据布局、分块计算、避免伪共享和 cache 冲突——这些优化的本质都是让 CPU 的缓存和预取器"看懂"你的访问模式，从而把昂贵的内存访问转化为廉价的缓存命中。曲线图的价值在于：它不仅告诉我们"哪个更快"，还精确揭示了"在什么工作集大小下开始出现差异"——这正是优化工作的切入点。
